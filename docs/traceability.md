# 規則對照表

依專案 `CLAUDE.md` 第 6 節第 2 點：每一個規則編號一列。狀態只有三種——**已驗證**（附測試或規則名稱）、**已實作未驗證**、**尚未實作**。

規則名稱（全大寫）是 `architecture-tests` 模組 `kanban.architecture.rules` 套件內的常數；每條都有「對正式程式碼」的測試與「對違規樣本」的咬人測試。

- 「對正式程式碼」讀入的是 `kanban` 底下全部的正式程式碼（`Imported.production()`），不列業務情境名稱。新業務情境的模組只要在 `architecture-tests` 的 classpath 上（目前經由 `kanban-main` 的相依帶進來），每一條規則都會檢查到。
- 新增一個業務情境要做的事——第二個情境「流程分析」實際做過的完整清單（第二階段，2026-11-17）：
  1. **建置**：根 `pom.xml` 的 `<modules>` 與 `dependencyManagement`；每一圈一個模組，內兩圈用 Maven Enforcer 限制相依（entities 零相依、use-cases 只相依自己的 entities；防腐層模組只允許列名的上下游 artifact）；內三圈寫 `module-info`。
  2. **聚合測試的寫法檢查（ES-5）**：把新情境 entities 模組的 test-jar 加進 `architecture-tests/pom.xml`，忘了加會被 `EntitiesRulesTest.ES5_每個有Entities圈的業務情境_它的聚合測試都讀得到` 擋下（依形狀找出所有有 entities 圈的情境，不列情境名稱；2026-11-17 反向證明：拿掉流程分析的 test-jar 時失敗）。
  3. **允許清單「加名字」（第二階段設計第 0 節 4d）**：`TOP_LEVEL_PACKAGES_SCREAM`、`ADAPTER_PACKAGES_ON_ALLOW_LIST`、`COMMAND_USE_CASES`／`QUERY_USE_CASES`、`WRITE_SIDE_GATEWAY_TYPES`、`JDBC_USERS`、`EntitiesRules` 的 Given／When／Then 工具與重播測試例外、聚合根的 record 例外、`STATE_CHANGES_ONLY_IN_APPLY` 的集合欄位初始值、`GlossaryTest` 的內部物件名稱。這些沒加會直接讓建置失敗，不會漏檢。
  4. **情境關係（DDD-3）**：`DddRules.CONTEXTS_INTEGRATE_ONLY_THROUGH_PUBLISHED_LANGUAGE` 的兩張表（上游公布哪個套件、下游哪個套件是防腐層），同時更新 `docs/context-map.md`。
  5. **用語（DDD-1）**：`docs/glossary.md` 加一節；`GlossaryTest` 依情境各自比對。
  6. **資料庫**：自己的 schema 與自己的 Flyway 版本紀錄；寫入端只有事件表的結構測試（ES-1）、事件表唯讀的測試（ES-2）。
  7. **Main**：一個組裝類別（Bean 名稱加情境前綴，避免同名被當成覆寫）、`KanbanApplication` 掃描新情境的薄殼套件；共用的資料庫連線依序更新兩邊的結構。
  8. **前端**：自己的 `web-ui` workspace；根目錄 `package.json` 的 workspaces 與 lint 路徑；`eslint.config.js` 為新情境加一行「各情境畫面互不引用」，並把它加進其他情境的禁止清單。
  9. **本表與審查清單**：每一列補上新情境的落點與測試；只能靠審查清單守的規則，對新情境做一次審查並記錄。
- 咬人測試（`Imported.assertBites`）必須看到規則回報「有違規」才算擋下；規則一個類別都沒選到（ArchUnit 的 failed to check any classes）不算。2026-11-16 加上這個條件後重跑，原有的咬人測試全部仍然成立。
