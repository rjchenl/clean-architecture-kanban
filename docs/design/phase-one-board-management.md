# 第一階段設計：看板管理

- 日期：2026-11-14
- 狀態：**使用者已於 2026-11-14 核可**（含第 4.3、4.4 節兩個規則解讀）。
- 依據：專案根目錄 `CLAUDE.md`（39 條規則）。本文件每個設計決定都標明它對應哪一條規則。

## 0. 先講三件你該先知道的事

1. **第一階段做完，39 條規則不會全部「已驗證」。** 只有一個業務情境時，「跨情境整合」（DDD-3）沒有東西可以整合，會留在「尚未實作」，要到第二階段加入「流程分析」才補得上。所以第一階段結束時，依 `CLAUDE.md` 第 6 節第 5 點，還**不能**宣稱「符合 DDD」，只能逐條列出狀態。預期狀態見第 11 節。
2. **有兩條規則照字面做不到，我採了較窄的解讀，需要你點頭。核可這份文件＝同意這兩個解讀。**
   - **CA-5**（見第 4.3 節）：「跨越邊界只能傳簡單資料」我解讀成管「畫面那一側」的邊界（Controller → Use Case → Presenter）；存取資料的 Repository 仍然收、回聚合，因為 DDD-8 明文規定 Repository「以聚合為單位、實作在外圈」，兩條照字面無法同時成立。
   - **CA-11 的 DIP**（見第 4.4 節）：「跨圈相依一律指向抽象」我解讀成管「行為」——外圈要呼叫內圈做事、內圈要外圈幫忙做事，都只能透過介面；外圈使用內圈的「資料型別」（聚合、值物件、領域事件）不算違反。照字面的話，Use Case 連看板聚合都不能直接用，做不出來。
3. **第一階段就包含真的資料庫（PostgreSQL）**，不是只做記憶體版。原因：CA-6 與 ES-1 的驗證方式都要求資料庫版實作存在，沒有它這兩條只能停在「未驗證」。

## 1. 目的與成功的樣子

**目的**：示範作品。讓讀者能逐條查核《Clean Architecture》、DDD、CQRS、Event Sourcing 四套方法真的被用上。功能只是載體。

**成功的樣子**

- 使用者在瀏覽器上能建立看板、管理欄位與卡片、拖動卡片；超過在製品上限時被拒絕並看到原因；能看到單張卡片的移動歷程。
- `docs/traceability.md` 對照表 39 列，每列指得到程式位置與守住它的檢查。
- 任何一條架構規則被違反，建置或測試就是紅燈，CI 每次推送都跑。

**不做（第一階段）**：「流程分析」第二業務情境、登入與多人權限、多人即時同步畫面、封存後的還原、卡片指派／標籤／到期日。

**做了就算失敗的事（即使功能能跑）**

- 用傳統「存現況」的資料表當寫入端依據，事件只是附帶記錄。
- 架構測試寫了但其實擋不住違規（所以每條架構測試都要附一個故意違規的樣本，見第 9 節）。
- Vue 裡出現業務判斷（例如前端自己算有沒有超過上限）。
- 為了讓 Spring 好接，把 Spring 註解放進內三圈。

## 3. 做法的選擇

### 3.1 聚合怎麼切（影響最大的決定）

| 做法 | 內容 | 取捨 |
|---|---|---|
| **A. 一個「看板」聚合，欄位與卡片是它內部的東西（採用）** | 在製品上限、「欄內有卡片不能刪欄」都由看板聚合用自己的狀態判斷 | 規則全部守得住，最單純。代價：同一個看板的所有操作共用一個版本號，兩個人同時改同一個看板的不同卡片，後送出的那個會被擋下要重試。第一階段沒有多人，可以接受 |
| B. 「看板」聚合管卡片放在哪，另一個「卡片」聚合管卡片內容 | 改卡片內容不會跟移動卡片搶版本號 | 「新增卡片」「刪除卡片」會一次改到兩個聚合，違反 DDD-5（一個指令只改一個聚合）；要改成事件串接才合規，第一階段不值得 |
| C. 每張卡片各自是聚合，在製品上限去查詢端數張數 | 併發衝突最少 | 寫入端用讀取模型做業務決定，直接違反 CQRS-4。不可行 |

採用 A。代價（看板級的版本衝突）寫進第 7 節的一致性說明。

### 3.2 怎麼守相依方向

| 做法 | 取捨 |
|---|---|
| **A. 每一圈是獨立的 Maven 模組＋內三圈加 Java 模組宣告（`module-info`）＋ArchUnit（採用）** | Maven 模組：內圈的建置設定裡根本沒有外圈，寫錯就編譯不過（CA-1）。`module-info`：每一圈只公開該給外面用的套件（例如第 2 圈只公開邊界介面與 Request／Response Model，Use Case 的實作類別不公開），第 3 圈想直接引用實作類別就編譯不過（CA-16）。兩者都擋不到的細節（套件命名、禁用註解）由 ArchUnit 補。第 4 圈與 Main 因為 Spring 的關係不加模組宣告，它們是最外圈，本來就可以看到全部 |
| B. 只有 Maven 模組＋ArchUnit，不加 `module-info` | 較省事，但跨圈要用的類別全部得是 `public`，「誰可以用」只剩 ArchUnit 在擋。`CLAUDE.md` 第 6 節規定能用較強的手段就不能只用較弱的，不合規 |
| C. 單一模組，只靠 ArchUnit | 最省事，同樣不合規 |

**尚未實測的風險**：內三圈加 `module-info` 後，與 Maven 測試外掛、ArchUnit、Spring Boot 啟動的搭配我還沒實際跑過。實作計畫的第一步就是做一個最小骨架驗證這件事；如果真的做不到，我會停下來回報，不會自己退回做法 B。

### 3.3 寫入後畫面多久看得到（CQRS-6）

| 做法 | 取捨 |
|---|---|
| **A. 同一個請求內同步更新讀取模型（採用）** | 指令回覆成功時，畫面資料已經是新的，使用者不會看到舊資料。萬一更新讀取模型那一步失敗，事件已經存好，下次有事件進來或系統啟動時會補上 |
| B. 背景非同步更新 | 更接近大型系統，但畫面要處理「剛改完卻還沒看到」，第一階段沒有必要。第二階段跨情境整合時再用 |

## 4. 結構

### 4.1 模組（每一圈一個建置模組）

```
clean-architecture-kanban/
├── board-management/              業務情境：看板管理（CA-10：最上層是業務名稱）
│   ├── entities/                  第 1 圈：看板聚合、值物件、領域事件。純 Java，零相依
│   ├── use-cases/                 第 2 圈：只相依 entities。零框架
│   ├── interface-adapters/        第 3 圈：Controller、Presenter、ViewModel、Gateway 轉接程式、Projection
│   ├── frameworks-drivers/        第 4 圈：Spring Web 薄殼、資料庫連線、資料庫結構
│   └── web-ui/                    第 4 圈：Vue 畫面（放在業務情境底下，CA-10）
├── main/                          Main 元件：建立所有物件並接起來（CA-8）
├── architecture-tests/            看得到全部模組的 ArchUnit 測試
└── docs/                          用語表、對照表、情境關係、審查清單、設計文件
```

套件：`kanban.boardmanagement.<圈>.…`。第 2 圈內再分 `commands.<use case 業務名稱>` 與 `queries.<use case 業務名稱>`（CA-10、CQRS-1）。

### 4.2 每一圈可以用什麼

| 圈 | 可以用 | 不可以用 |
|---|---|---|
| entities | JDK | 其他一切 |
| use-cases | JDK、entities | 其他一切 |
| interface-adapters | JDK（含 `java.sql`）、內兩圈、Jackson（只用來把事件與讀取模型轉成 JSON） | Spring、Jakarta、資料庫驅動程式 |
| frameworks-drivers、main | 全部 | — |

Jackson 放在第 3 圈是我的判斷：這一圈的職責就是轉換資料格式，而 SQL 依書上也屬於這一圈。CA-7 的「等」在本專案定義為：Spring、Jakarta、資料庫驅動程式、連線池、資料庫版本管理工具。

內兩圈的模組另用 Maven Enforcer 設定「不得宣告任何非測試相依」，違反就建置失敗。

### 4.3 CA-5 的解讀（需你點頭）

- **畫面那一側的邊界**（Input Boundary、Output Boundary）：參數與回傳只能是 Request Model／Response Model，由 JDK 基本型別、字串、列舉、這些東西的清單與 record 組成。聚合、值物件、領域事件都不准出現。架構測試守。
- **資料那一側的邊界**（Repository、Event Store）：`BoardRepository` 收、回看板聚合；`EventStore` 收、回領域事件。理由是 DDD-8 與 CA-6 規定介面在第 2 圈、實作在外圈，實作必然拿到聚合。資料庫資料列、SQL、JSON 都不會穿過這條邊界進到第 2 圈。
- 讀取模型的 Gateway 只回傳第 2 圈查詢端自己定義的簡單資料。

### 4.4 CA-11 的 DIP 與 ISP 具體檢查什麼（DIP 的解讀需你點頭）

**DIP**

- 內圈需要外圈幫忙（存資料、拿時間、產生識別碼、交出結果）：一律呼叫內圈自己定義的介面。由編譯守（內圈看不到外圈）。
- 外圈要內圈做事：第 3 圈只能透過 Input Boundary 介面呼叫 Use Case，引用不到 Use Case 的實作類別。由 `module-info` 守（實作類別的套件不公開）。
- 只有 Main 可以引用 Use Case 實作類別與轉接程式的具體類別。由 ArchUnit 守。
- 外圈使用內圈的資料型別（聚合、值物件、領域事件、Request／Response Model）不算違反。

**ISP**

- 每個 Use Case 有自己的 Input Boundary（只有一個方法）與自己的 Output Boundary，不共用一個大介面。
- 事件存取拆成兩個介面：`EventStore`（讀某條事件串流、新增事件）只給 `BoardRepository` 的實作用；`EventFeed`（從某個位置之後依序讀出全部事件）只給 Projection 用。
- 讀取模型拆成「唯讀介面」（查詢 Use Case 用）與「寫入介面」（只有 Projection 用）。
- ArchUnit 檢查：上述每個介面只被指定的使用者引用。

## 5. 領域模型（entities 圈）

### 5.1 聚合：看板（Board）

看板聚合內含欄位（有順序）與卡片（每欄內有順序）。外部只能呼叫聚合根的方法；欄位與卡片物件不外露（DDD-4）。

**值物件**（DDD-6，全部不可變、建立時自我驗證）：`BoardId`、`BoardName`、`ColumnId`、`ColumnName`、`WipLimit`、`CardId`、`CardTitle`、`CardDescription`、`Position`（欄位在看板上、或卡片在欄內排第幾個）。

### 5.2 業務規則（每條一支聚合測試）

標「使用者」的是你指定的；標「預設」的是我先採的保守預設，你可以改。

| # | 規則 | 來源 |
|---|---|---|
| R1 | 欄內還有卡片，不能刪除該欄 | 使用者 |
| R2 | 把卡片移入或新增到某欄，若會超過該欄的在製品上限，拒絕 | 使用者 |
| R3 | 欄內排序不受在製品上限影響（張數沒變） | 預設 |
| R4 | 在製品上限是正整數；沒設定代表無上限；可以取消上限 | 預設 |
| R5 | 把上限設成比欄內目前張數還低，拒絕（要先移走卡片） | 預設 |
| R6 | 看板名稱、欄位名稱、卡片標題不可空白，最長 100 字；卡片說明可空白，最長 2000 字 | 預設 |
| R7 | 同一個看板內，欄位名稱不可重複 | 預設 |
| R8 | 已封存的看板拒絕所有變更；第一階段封存後不能還原 | 預設 |
| R9 | 新看板沒有任何欄位；新欄位加在最右邊；新卡片加在該欄最下面 | 預設 |
| R10 | 移動卡片的目標欄必須在同一個看板內；目標位置超出範圍，拒絕 | 預設 |
| R11 | 把東西移到它原本的位置：算成功，但不產生事件 | 預設 |
| R12 | 操作不存在的欄位或卡片，拒絕 | 預設 |

拒絕原因是一個列舉（名稱進用語表），由 Presenter 轉成中文訊息。

### 5.3 領域事件（DDD-7：過去式、不可變）

`BoardCreated`、`BoardRenamed`、`BoardArchived`、`ColumnAdded`、`ColumnRenamed`、`ColumnMoved`、`ColumnWipLimitSet`、`ColumnWipLimitRemoved`、`ColumnRemoved`、`CardAdded`、`CardContentChanged`、`CardMoved`（換欄）、`CardRepositioned`（欄內排序）、`CardRemoved`。

每個事件都帶：看板識別碼、發生時間。時間與新識別碼由 Use Case 從外部介面取得後傳進聚合，聚合自己不讀時鐘、不產生亂數（ES-4）。

### 5.4 事件溯源的寫法（ES-3）

- 指令方法（例如 `moveCard(...)`）：檢查規則 → 決定產生哪些事件 → 交給套用方法。
- 套用方法：只改狀態，不檢查、不會失敗、沒有副作用。
- 載入聚合＝從空白開始依序套用它的全部事件。

## 6. Use Case 圈

### 6.1 指令端（14 個）

`CreateBoard`、`RenameBoard`、`ArchiveBoard`、`AddColumn`、`RenameColumn`、`MoveColumn`、`SetColumnWipLimit`、`RemoveColumnWipLimit`、`RemoveColumn`、`AddCard`、`ChangeCardContent`、`MoveCard`、`RepositionCard`、`RemoveCard`

每個 Use Case 的形狀相同（CA-4、DDD-9）：

1. 定義 Input Boundary（只收 Request Model）與 Output Boundary（只收 Response Model）。Use Case 實作在建立時就拿到它的 Output Boundary，由 Main 給。
2. 實作只做協調：從 `BoardRepository` 取出看板 → 呼叫聚合的一個方法 → 存回去 → 把結果交給 Output Boundary。Use Case 本身不回傳任何東西。
3. Response Model 只有：成功或失敗、拒絕原因、必要的識別碼（CQRS-2）。

指令端的 Gateway 介面：`BoardRepository`（載入、儲存）、`EventStore`（讀取某條事件串流、帶預期版本號新增事件；**沒有更新與刪除**）、時間來源、識別碼產生器。

### 6.2 查詢端（3 個）

`ViewBoard`（看板現況）、`ViewCardHistory`（卡片移動歷程）、`ListBoards`（看板清單，我加的）。

查詢 Use Case 一樣走 Input／Output Boundary，只讀查詢端自己的讀取模型 Gateway（唯讀介面）。查詢端的套件不引用指令端的任何東西，也不引用聚合、`BoardRepository`、`EventStore`（CQRS-1、CQRS-3）。

**卡片移動歷程是一份讀取模型**，由 Projection 根據事件整理出來；查詢端不去讀事件紀錄。歷程列出：卡片何時被新增到哪一欄、每次從哪一欄換到哪一欄、何時被刪除。不列欄內排序與內容修改。欄位名稱顯示事件發生當時的名稱（之後欄位改名或被刪，舊歷程不變）。

## 7. Interface Adapters 圈

### 7.1 一次請求怎麼走

```
瀏覽器 → Spring 薄殼（第 4 圈，只收 HTTP、轉給 Controller）
       → Main 提供的組裝程式：為這次請求建立 Presenter、Use Case（把 Presenter 當 Output Boundary 交給它）、Controller
       → Controller（第 3 圈，純 Java）：把輸入組成 Request Model，呼叫 Input Boundary
       → Use Case（第 2 圈）→ 聚合
       → Output Boundary ←實作— Presenter（第 3 圈）：把 Response Model 整理成 ViewModel
       → 組裝程式從 Presenter 取出 ViewModel 交還薄殼 → 薄殼原樣輸出成 JSON
```

Controller 不認識 Presenter，Presenter 不認識 Controller；只有 Main 知道誰接誰（CA-8）。薄殼呼叫的是第 4 圈自己定義的介面，由 Main 實作。Use Case 與 Presenter 都很輕，每次請求新建一組，不共用狀態。

Spring 薄殼不含任何判斷；HTTP 狀態碼由 ViewModel 裡的一個結果列舉一對一換算。

### 7.2 Presenter 與 ViewModel（CA-9）

ViewModel 只有字串、布林、列舉與它們的清單。所有格式整理都在 Presenter：時間轉成顯示用字串（時區由 Main 傳入，預設 Asia/Taipei）、在製品數量轉成「3 / 5」這種字串、拒絕原因轉成中文訊息。

畫面**不**顯示「這一欄已滿」的標記：判斷滿不滿就是拿張數比上限，是業務規則（R2），Presenter、Projection、Vue 都不准做（DDD-9）。使用者從「2 / 3」看得出數量；真的放不進去時，由聚合拒絕並回覆原因。

看板現況畫面拿到的資料長這樣：

```
看板名稱：「產品開發」            [已封存：否]
┌ 待辦 ─────────┐ ┌ 進行中 ── 2 / 3 ┐ ┌ 完成 ─────────┐
│ ▢ 設計登入頁   │ │ ▢ 串接金流       │ │ ▢ 建立專案     │
│ ▢ 寫用語表     │ │ ▢ 寫架構測試     │ │                │
└────────────────┘ └──────────────────┘ └────────────────┘
```

### 7.3 Gateway 轉接程式

- `EventStore`：記憶體版與 PostgreSQL 版（用 JDK 的 `java.sql`，連線來源由 Main 注入）。
- `BoardRepository`：一個實作，底下用 `EventStore`——載入時重播事件，儲存時把新事件帶著預期版本號寫入。
- 讀取模型：記憶體版與 PostgreSQL 版。
- 事件轉 JSON：每種事件有固定的類型名稱與格式版本號；舊格式由轉換程式（upcaster）在讀出時轉成新格式，資料庫裡的舊資料永遠不動（ES-7）。

### 7.4 Projection（CQRS-5、ES-8）

- 事件寫入並提交之後，同一個請求內叫 Projection「去補到最新」。Projection 不是收別人推過來的單一事件，而是自己從 `EventFeed` 依序讀出「上次處理位置之後」的全部事件來處理，所以不會跳號、不會漏。
- 同一個 Projection 同一時間只有一個在補（用鎖），處理事件與更新處理位置在同一個交易內。
- 位置不比處理位置新的事件直接略過，所以同一個事件處理兩次結果不變。
- 讀取模型的寫入方法只有 Projection 呼叫得到（存取修飾詞＋架構測試）。
- 重建：清空讀取模型與處理位置，從第一筆事件重播。系統啟動時會自動把落後的補上。

### 7.5 一致性說明（CQRS-6）

事件寫入與讀取模型更新是**兩個各自獨立的交易**，先後在同一個請求內完成。分三種情況：

1. **正常**：指令回覆成功時，讀取模型已補到最新，緊接著查詢看得到新資料。
2. **讀取模型更新失敗**（例如 Projection 出錯）：事件已經存好，指令仍回覆成功，但這時查詢看到的是舊資料。讀取模型會在下一次任何指令成功後、或系統啟動時自動補上。這是本設計唯一會看到舊資料的情況。
3. **兩個請求同時改同一個看板**：先寫入的成功，後寫入的因版本號不符被拒絕，畫面顯示「看板已被更新，請重新整理後再試」。第一階段不自動重試。

三種情況各有一支整合測試（見第 9 節）。

## 8. Frameworks & Drivers 圈與 Main

- **資料庫結構**：寫入端只有一張事件表（全域序號、串流識別碼、串流內版本號、事件類型、格式版本號、內容 JSON、發生時間）。`(串流識別碼, 版本號)` 唯一，這就是樂觀鎖（ES-6）。資料庫另設觸發程序，對事件表做更新或刪除一律報錯（ES-2）。讀取模型的表另外放、可整批清掉。
- **寫入順序**：寫入事件時取一把資料庫層級的鎖，保證全域序號的順序等於實際寫入完成的順序，Projection 才不會漏掉事件。第一階段流量小，可接受。
- **Spring 薄殼**：REST 端點，每個端點一行轉給對應的 Controller。
- **Main**：Spring Boot 啟動類別加一個設定類別，用 `new` 建立所有 Use Case、轉接程式、Projection 並接起來。內三圈沒有任何註解，所以不靠掃描。記憶體版或資料庫版由設定值切換。
- **前端**：Vue 元件只把 ViewModel 顯示出來、把使用者的動作送成指令。拖動卡片＝送出「移到哪一欄第幾個位置」，成功或被拒絕都重新讀一次看板現況；前端不自己判斷能不能放。

## 9. 驗證設計

1. **編譯**：模組相依方向；內兩圈零相依（Maven Enforcer）。
2. **架構測試（ArchUnit）**：放在 `architecture-tests` 模組。**每一條規則都附一組故意違規的樣本類別，並有測試證明規則遇到它會紅**——否則無法區分「沒違規」和「規則根本沒在檢查」。
3. **聚合測試**：一律 Given 已發生的事件／When 指令／Then 產生的事件或被拒絕（ES-5）。R1～R12 每條至少一支。
4. **重播測試**：同一串事件重播多次，結果相同（ES-4）。
5. **契約測試**：同一套測試對記憶體版與 PostgreSQL 版各跑一次——Event Store（含只能新增、樂觀鎖）、讀取模型。
6. **事件格式相容測試**：每個事件每個格式版本存一份 JSON 樣本檔，樣本檔只增不改，測試確認都讀得回來（ES-7）。
7. **Projection 測試**：冪等（同一事件送兩次）、重建（清空重播後與清空前相同）。
8. **Use Case 測試**：用記憶體版 Gateway，不啟動 Spring（CA-3）。
9. **Presenter 單元測試**（CA-9）。
10. **整合測試**：啟動整個系統接 PostgreSQL，對應第 7.5 節三種情況各一支——送指令後立刻查詢看得到；故意讓 Projection 失敗一次，確認指令仍成功、查詢是舊資料、下一次指令後補上；兩個請求搶同一個看板，後者被拒絕（CQRS-6）。另有資料庫結構檢查：寫入端只有事件表（ES-1）。
11. **用語表測試**：entities 圈所有公開類別名稱、指令 Request Model 名稱都必須出現在 `docs/glossary.md`（DDD-1）。
12. **審查清單**：`docs/review-checklist.md`，守 SRP、OCP、LSP、CA-13、CA-15、DDD-9、前端不含業務判斷等只能靠人看的規則；每次審查的日期與結果記進對照表。
13. **瀏覽器實測**：第一階段收尾時在瀏覽器把第 2 節的每個操作實際走一遍。
14. **CI**：GitHub Actions 每次推送跑 1～11。

## 10. 邊界清單（CA-14）

| 邊界 | 隔開了什麼 | 為什麼會以不同理由改變 |
|---|---|---|
| entities ↔ use-cases | 看板本身的規則 ↔ 這個應用程式提供哪些操作 | 規則因業務政策而改；操作因產品功能而改 |
| use-cases ↔ interface-adapters（畫面側） | 操作的結果 ↔ 畫面要怎麼呈現 | 文字、格式、排版常改，不該動到操作 |
| use-cases ↔ interface-adapters（資料側） | 需要存取什麼 ↔ 怎麼存 | 換儲存方式不該動到操作 |
| interface-adapters ↔ frameworks-drivers | 轉換邏輯 ↔ Spring、PostgreSQL、HTTP | 框架升級、換資料庫 |
| 指令端 ↔ 查詢端 | 改變狀態 ↔ 給畫面看的資料 | 畫面需求變動遠比業務規則頻繁 |
| 後端 ↔ Vue | 整理好的 ViewModel ↔ 顯示 | 視覺改版不該動到後端 |
