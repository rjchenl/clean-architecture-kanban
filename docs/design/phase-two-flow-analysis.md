## 0. 先講你該先知道的事

1. **這一階段補的是 DDD-3（跨情境整合）**，也就是 39 條裡唯一還「尚未實作」的那條。2026-11-16 查 `docs/traceability.md`：只有 DDD-3 那一列是「尚未實作」，沒有任何一列是「已實作未驗證」。做完之後的目標是 39 條全部「已驗證」；能不能宣稱「符合四套方法」，仍照 `CLAUDE.md` 第 6 節第 5 點，跑完整建置、逐條確認對照表後才說。
2. **已經跟你確認過的三件事**（2026-11-16）：
   - 流程分析採做法 B：流程分析有自己要決定的事（哪一欄算開始、哪一欄算完成、放幾天算卡住），有自己的聚合、指令與事件（第 3.1 節）。
   - 改了階段設定，整段歷史照新設定重算（第 3.3 節）。
   - 兩個情境的接法照書定：看板管理公布一份固定格式的「看板動態」，流程分析在背景定時去讀，用自己的防腐層翻成自己的用語（第 3.2 節）。
3. **看板管理也會改，但只加不改，而且不含任何流程分析的概念。** 它會多一份對外公布的看板動態紀錄，內容只用看板管理自己的用語（看板、欄位、卡片、移動），沒有「階段」「完成」「卡住」。之後別的情境也能讀同一份。這和你否決的做法 C（把「完成欄」做進看板管理）不同。
4. **需要你點頭的規則解讀與檢查調整（使用者 2026-11-17 已同意以下四項）。**
   - **(a) 編譯器擋不到的一處（CA-16）**：防腐層所在的模組必須引用看板管理的「讀取看板動態」查詢介面，而看板管理的 Use Cases 模組宣告 `requires transitive` 領域模組（`board-management/use-cases/src/main/java/module-info.java`），所以防腐層模組在編譯時看得到看板管理的領域類別，只能靠架構測試擋。
     - 流程分析的 entities、use-cases、interface-adapters 三個模組完全看不到看板管理，由編譯器擋。
     - frameworks-drivers 與 Main 是最外圈，本來就看得到全部；web-ui 不是 Java 模組。這三個由架構測試擋。
     - 要讓編譯器連防腐層也擋，得把看板管理的公布格式拆成獨立模組，這會讓兩支既有的模組相依測試（`UseCaseRulesTest` 的 CA-3、CA-7 兩支）的允許清單變寬。依 `CLAUDE.md` 第 0 節第 5 點我不自己做；你要做的話，請在核可時說明。
   - **(b) CA-5 的第三種邊界**：第一階段把 CA-5 解讀成管「畫面那一側」，資料那一側的 Repository 收、回聚合（第一階段 4.3 節）。情境之間的邊界比照畫面那一側：只傳簡單資料（字串、數字、時間、列舉、這些的清單與 record）。由架構測試守。
   - **(c) DDD-9 的範圍**：Projection 可以把領域模型**已經判斷好的結果**做加總、平均、按週計數；**不可以自己判斷**，例如什麼算開始、什麼算完成、交付時間怎麼算、算不算卡住。這些判斷一律由聚合做，結果記在事件裡。
     - 「每週從週一 00:00 起算、用哪個時區」「顯示最近 8 週」「平均與最長怎麼算」我歸為**統計方式**，不是業務規則：它們只決定把已經判斷好的結果怎麼分組、怎麼加總，不決定任何一個工作項目算不算完成。
     - 這幾項列在第 7.4 節的統計方式表（S1、S2），由 Projection 測試守，不用聚合測試。
     - 時區由 Main 傳入（預設 Asia/Taipei）。
     - 由審查清單守，並寫進 `docs/review-checklist.md`。
   - **(d) 會擴充的允許清單**：下面幾份清單本來就是「新增東西時要同步改」的設計（有的在程式註解裡寫明「多一個就要先改這條規則」），判斷依據都不變，所以我把它們算作擴充、不算放寬：

     | 清單 | 位置 | 要加什麼 |
     |---|---|---|
     | 最上層套件（CA-10） | `CleanArchitectureRules.topLevelPackagesScream` | `kanban.flowanalysis` 底下的四圈 |
     | Use Case 套件允許清單（CA-10） | `UseCaseRules.ALLOWED_USE_CASE_PACKAGES` | 流程分析的指令與查詢、看板管理的 `readboardactivities` |
     | 指令端 Gateway 型別（ES-1） | `EventSourcingRules.WRITE_SIDE_GATEWAY_TYPES` | `BoardFlowRepository` |
     | 可以用 JDBC 的類別（ES-1） | `EventSourcingRules.JDBC_USERS` | 防腐層的讀取位置儲存、看板動態紀錄的儲存（實作計畫定名稱） |
     | 看板管理資料庫裡的表（ES-1） | `WriteSideSchemaTest.寫入端只有事件表` | 讀取模型表 `board_activity_log` |
     | 聚合測試寫法的例外（ES-5） | `EntitiesRules` 的 `BoardScenario`／`ReplayTest` 兩項 | 流程分析的 Given／When／Then 工具與重播測試 |
     | 架構測試讀入的測試程式（ES-5） | `architecture-tests/pom.xml` | 流程分析 entities 模組的 test-jar |

     | 值物件與事件必須是 record 的例外（DDD-6、DDD-7） | `EntitiesRules.VALUE_OBJECTS_AND_EVENTS_ARE_RECORDS` 的 `Board`、`BusinessRuleViolation` 兩項 | 流程分析的聚合根 `BoardFlow` 與它的例外類別 |

## 1. 目的與成功的樣子

**整個專案的用途**（使用者 2026-11-17 強調）：示範整套軟體架構規則，讓 AI 照著實踐。所以每一個設計決定都先問「AI 照這條規則寫，偏離時會不會被自動檢查擋下」，功能多寡其次。

**這一階段的目的**：示範作品的第二個業務情境。讓讀者能查核兩件第一階段查核不到的事：
1. 兩個情境之間怎麼整合，又不共用領域模型（DDD-2、DDD-3）；
2. 四套方法在第二個情境裡同樣成立。

**成功的樣子**

- 使用者在看板頁按「流程分析」，進到流程分析頁，可以：
  - 替每一欄指定階段；
  - 設定卡住門檻；
  - 看到每一欄的階段、目前張數、平均停留時間；
  - 看到最近 8 週每週完成幾張、交付時間的平均與最長；
  - 看到哪些卡片卡住了。
- 在看板上操作之後，流程分析的數字幾秒內跟著變。
- 改了階段設定，整段歷史照新設定重算，包括流程分析上線前、第一階段以來的歷史。
- 對照表 39 列全部「已驗證」，DDD-3 有架構測試守。

**不做（第二階段）**：
- 跨看板的彙總；
- 圖表；
- 預測完成日；
- 累積流量圖；
- 匯出；
- 登入與權限；
- 第一階段「不做」清單裡的項目照舊不做。

**做了就算失敗的事（即使功能能跑）**

- 流程分析引用看板管理的領域類別，或直接讀看板管理的事件表。
- 「什麼算開始、什麼算完成、交付時間多長、算不算卡住」的判斷，出現在 Projection、Presenter、查詢端或 Vue。
- 看板管理裡出現任何流程分析的概念（階段、完成、卡住）。
- 為了讓新情境通過檢查，而放寬既有的架構測試。

## 3. 做法的選擇

### 3.1 流程分析做成哪一種（使用者已選 B）

| 做法 | 內容 | 照書判定 |
|---|---|---|
| A. 只把事件換算成數字 | 停留時間、每欄張數；沒有使用者的設定 | 照最初寫法（計算放在 Projection）**不符合**：業務規則要在內兩圈（第 20、22 章）。把計算移進流程分析的 Entities 圈後才符合 |
| **B. 流程分析有自己要決定的事（採用）** | 使用者在流程分析裡設定階段與卡住門檻；有自己的聚合、指令、事件 | **符合**：設定屬於量測流程的人，放在流程分析符合 SRP（第 7 章）。邊界畫在「團隊怎麼用看板」和「怎麼量測流程」之間，兩者會以不同理由改變（第 13、16～19 章） |
| C. 把「完成欄」做進看板管理 | 看板管理多一個概念，只為了讓流程分析算得出來 | **不符合**：看板管理會因為流程分析的需求而改，同一個模組變成服務兩種角色（第 7 章 SRP 的反例） |

### 3.2 兩個情境怎麼接（照書定）

| 做法 | 照書判定 | 原因 |
|---|---|---|
| **1. 看板管理公布一份固定格式的看板動態，流程分析在背景定時去讀，用自己的防腐層翻譯（採用）** | 符合 | <ul><li>相依方向只從流程分析指向看板管理公布的格式，看板管理不知道流程分析存在（第 22 章相依性規則）。</li><li>公布的格式只有簡單資料（第 22 章「跨越邊界的資料」）。</li><li>看板管理內部的存法怎麼改，只要公布格式不變，流程分析都不受影響（第 14 章：往穩定的方向相依）。</li></ul> |
| 2. 流程分析直接讀看板管理的事件表 | 不符合 | 事件表是看板管理寫入端自己的存法（`V1__event_store.sql`），連格式轉換程式都在看板管理內部（`BoardEventJson`）。直接讀，等於依賴另一個情境的資料庫細節（第 30 章、第 14 章） |
| 3. 看板管理寫完事件後直接推給流程分析 | 相依方向符合，但不採用 | 流程分析出錯或系統重啟時，推漏的事件補不回來；也讀不到第一階段以來的歷史 |
| 4. 拆成兩個獨立服務，中間加訊息佇列 | 書沒有要求，現在不做 | 第 16、27 章：服務是部署方式，不是架構。邊界畫對了，之後隨時拆得開 |

做法 1 要配合三條現有規則，所以形狀是固定的：

- **CA-11 ISP**：`EventFeed` 只能給 `adapters.eventstore` 與 `adapters.projection` 用（`CleanArchitectureRules.EVENT_ACCESS_IS_SEGREGATED`）。所以看板管理要由一個真正的 Projection 把領域事件翻成公布格式，存成一份讀取模型（看板動態紀錄）。
- **CQRS-3**：查詢端不得讀事件紀錄（`CqrsRules.QUERIES_NEVER_TOUCH_WRITE_SIDE`）。所以公布的方式是看板管理的一個查詢 Use Case「讀取看板動態」，它只讀那份讀取模型。
- **CQRS-3、DDD-9**：查詢端不得引用領域模型，Projection 不得做業務判斷。所以流程分析的計算不能放在查詢端或 Projection，只能走這條路：

  ```
  防腐層 → 流程分析的指令 → 聚合判斷 → 結果記在流程分析自己的事件裡 → Projection 存起來 → 查詢
  ```

### 3.3 改了設定之後，過去的數字怎麼算（使用者已選「重算」）

- 數字一律照目前的設定，對整段歷史計算。
- 原因：流程分析上線時，看板上已經有第一階段以來的歷史，但第一次設定之前沒有任何設定。如果設定只影響之後，第一次設定前就做完的卡片，全部不會算進數字。
- 代價：聚合要保存每個工作項目完整的移動紀錄。每改一次設定，結果有變的工作項目各新增一筆「流程結果更新」事件。舊事件不動（ES-2）。

### 3.4 聚合怎麼切

| 做法 | 內容 | 取捨 |
|---|---|---|
| **A. 每個看板一個「看板流程」聚合，設定與移動紀錄都在裡面（採用）** | 判斷時同時用到設定與移動紀錄，都在同一個聚合內 | <p>規則全部守得住。</p><p>代價一：背景同步和使用者改設定寫的是同一條事件串流，兩邊可能碰撞。背景那一邊自動重試；使用者這一邊看到「已被更新，請重新整理」，和第一階段相同。</p><p>代價二：聚合隨看板歷史變大，每次載入都要重播整段。示範規模可以接受，第二階段不做快照</p> |
| B. 設定一個聚合、移動紀錄另一個聚合 | 碰撞較少 | 判斷要同時用到兩個聚合。專案規則規定一個指令只能有一個 Repository（`UseCaseRules.ONE_AGGREGATE_PER_COMMAND`，DDD-5），做不到 |
| C. 每個工作項目一個聚合 | 碰撞最少 | 改設定要重算所有工作項目，一個指令會改到很多個聚合，違反 DDD-5 |

照書判定：書不談聚合，三種做法都能把規則放在 Entities 圈。決定性的限制是專案的 DDD-5。

### 3.5 「卡住」怎麼判斷

「卡住」是時間經過就會成立的事，沒有對應的看板事件。

| 做法 | 照書判定 | 原因 |
|---|---|---|
| **a. 系統定時送「檢查卡住的工作項目」指令，帶入現在的時間，由聚合判斷（採用）** | 符合 | 判斷在 Entities 圈（第 20 章）；時間由外部傳入，聚合不讀時鐘（ES-4）。代價：卡住的標記最多晚一個檢查週期（預設 10 分鐘）才出現 |
| b. 查詢時拿現在時間去比 | 不符合專案規則 | 查詢端不得引用領域模型（CQRS-3），判斷又不能放在查詢端（DDD-9） |
| c. Presenter 或 Vue 拿現在時間去比 | 不符合 | Humble Object 不得含業務規則（第 23 章，CA-9） |

### 3.6 寫入後多久看得到（CQRS-6）

第一階段設計第 3.3 節已定：跨情境整合時用背景更新。詳細說明見第 7.6 節。

## 4. 結構

### 4.1 模組

```
clean-architecture-kanban/
├── board-management/                 （既有）只加不改，見 4.3
├── flow-analysis/                    業務情境：流程分析（CA-10）
│   ├── entities/                     第 1 圈：看板流程聚合、值物件、領域事件。零相依
│   ├── use-cases/                    第 2 圈：只相依 flow-analysis/entities。零框架
│   ├── interface-adapters/           第 3 圈：Controller、Presenter、ViewModel、Gateway 轉接、Projection。不認識看板管理
│   ├── board-activity-translation/   第 3 圈：防腐層。唯一認識看板管理的模組
│   ├── frameworks-drivers/           第 4 圈：Spring Web 薄殼、資料庫結構、背景排程
│   └── web-ui/                       第 4 圈：流程分析的畫面元件
├── main/                             Main：多一份流程分析的組裝；前端的進入點也搬到這裡（見第 8 節）
├── architecture-tests/
└── docs/
```

- 套件：`kanban.flowanalysis.<圈>.…`；防腐層是 `kanban.flowanalysis.adapters.boardactivity`。
- 內三圈同樣加 `module-info`（CA-16），並用 Maven Enforcer 限制內兩圈不得宣告任何非測試相依。

### 4.2 每一圈可以用什麼

| 模組 | 可以用 | 不可以用 |
|---|---|---|
| flow-analysis/entities | JDK | 其他一切 |
| flow-analysis/use-cases | JDK、flow-analysis/entities | 其他一切 |
| flow-analysis/interface-adapters | JDK（含 `java.sql`）、流程分析內兩圈、Jackson | Spring、Jakarta、資料庫驅動程式、看板管理的任何東西 |
| flow-analysis/board-activity-translation | JDK（含 `java.sql`，只用在讀取位置的儲存）、流程分析的 use-cases、看板管理 `usecases.queries.readboardactivities` 套件 | 看板管理的其他任何套件（編譯時看得到，由架構測試擋，見第 0 節 4a） |

### 4.3 看板管理要加什麼（只加不改）

| 圈 | 新增 | 作用 |
|---|---|---|
| use-cases | 查詢 `queries.readboardactivities`：`ReadBoardActivitiesInput`／`Output`／`Request`／`Response`；公布格式 `BoardActivity`（record）、`BoardActivityKind`（列舉）；Gateway `BoardActivityReader` | 「讀取某個位置之後的看板動態」，只讀看板動態紀錄這份讀取模型（CQRS-3） |
| interface-adapters | Projection `BoardActivityProjection`；看板動態紀錄的儲存（記憶體版、PostgreSQL 版） | 把看板管理的領域事件翻成公布格式（只是格式轉換，沒有業務判斷） |
| frameworks-drivers | 資料庫版本 `V3__board_activity_log.sql` | 看板動態紀錄的表（讀取模型，可以清掉重建） |
| main | 事件寫入後，同一個請求內也叫這個 Projection 補到最新 | 和現有兩個 Projection 一樣的時機 |

照書判定（和你否決的做法 C 差在哪）：
- 做法 C 是把流程分析的概念「完成欄」做進看板管理，看板管理會因為量測流程的人而改，違反 SRP（第 7 章）。
- 這裡加的只是看板管理用自己的用語，對外公布自己已經發生的事。它不知道下游是誰、下游怎麼用。下游改變想看的數字時，看板管理不用動。
- 對外公布的是穩定、抽象的東西，別的元件往它相依，正是第 14 章的穩定相依、穩定抽象原則（SDP、SAP）要的方向。
- 公布哪些種類，是依目前唯一的下游需要挑的（第 4.4 節）。沒有人用的不先公布，之後要加只新增種類。

### 4.4 跨情境邊界（DDD-3、CA-5）

- **看板動態**（公布格式）：
  - 看板動態是同一個程式裡傳遞的 Java record（`BoardActivity`）加上種類列舉（`BoardActivityKind`），和看板管理事件表的存法分開。事件表的格式改了，只要看板動態不變，下游就不受影響。
  - 只含簡單資料（第 0 節 4b）。
- **相容承諾綁在 Java 型別上**：
  - 兩個情境在同一次建置裡編譯，改動看板動態的型別，防腐層會直接編譯失敗。
  - 另有一支「公布格式契約測試」：釘住每一種動態與它的欄位名稱和型別。新增種類或欄位會通過，刪除或改名既有的種類、欄位會失敗。
  - 看板動態紀錄（`board_activity_log`）是可以清掉重建的讀取模型，重建後一律是最新的寫法，不做格式版本。
  - 之後真的拆成獨立服務、要跨程式傳遞時，才需要序列化格式的版本，第二階段不做。
- **位置**：看板動態的位置＝它來源事件在事件表的全域序號。看板動態紀錄清掉重建後，位置完全一樣，流程分析已經讀到的位置仍然有效（ES-8）。
- **公布哪些動態**：

  | 看板管理的事 | 公布嗎 |
  |---|---|
  | 看板建立、改名、封存 | 公布 |
  | 欄位新增、改名、調整順序、刪除 | 公布 |
  | 卡片新增、換欄、刪除 | 公布 |
  | 卡片內容修改 | 公布，只帶標題，不帶說明 |
  | 欄內排序、在製品上限的設定與取消 | 不公布：沒有下游需要。之後要加只新增種類，不改舊種類 |

- **防腐層**的工作：
  1. 讀看板動態；
  2. 翻成流程分析的用語（欄位→流程欄位、卡片→工作項目）；
  3. 組成流程分析的 Request Model，呼叫「記錄看板動態」指令。

  看板管理的任何型別都不會越過防腐層。
- **上游新增一種動態時**：防腐層對種類列舉逐一列出每一種，不用「其他」分支（Java 的 switch 運算式不寫 default，沒列到就編譯失敗）。所以看板管理一新增種類，防腐層就編譯不過，一定要有人明確決定「翻譯」或「不需要、略過」。執行時不會出現不認得的種類。

### 4.5 同一件事在兩個情境的名字（DDD-2）

| 看板管理 | 流程分析 | 差在哪 |
|---|---|---|
| 看板 `Board` | 看板流程 `BoardFlow` | 流程分析只關心一個看板「流過哪些欄、花了多久」，不管欄位上限與卡片內容 |
| 欄位 `Column` | 流程欄位 `FlowColumn` | 流程分析的欄位多一個「階段」；刪掉後階段仍保留，用來判斷歷史 |
| 卡片 `Card` | 工作項目 `WorkItem` | 流程分析只記它什麼時候進出哪一欄、標題（顯示用） |
| （沒有） | 階段、開始時間、完成時間、交付時間、停留時間、卡住、卡住門檻 | 只存在於流程分析 |

名稱定稿前先進用語表（DDD-1）。流程分析的內部物件名稱不得與看板管理相同：DDD-4 的「內部物件不得公開」規則依用語表的名稱、不分套件檢查，同名會互相干擾。

### 4.6 沿用既有規則認得的名稱

既有的架構規則有一部分靠名稱認對象。流程分析沿用這些名稱，才會被同一批規則檢查到，不用另外改規則：

| 對象 | 必須叫什麼 | 靠它的規則 |
|---|---|---|
| 領域事件的共同介面 | 名稱以 `Event` 結尾 | DDD-7（`DOMAIN_EVENT`） |
| 聚合的記帳欄位與方法 | `persistedVersion`、`pendingEvents`；`record`、`markCommitted`、`rehydrate`、`uncommittedEvents` | ES-3、ES-5 |
| 指令的回覆 | `CommandResponse`，欄位恰好是 `succeeded`、`failureCode`、`createdId` | CQRS-2 |
| Use Case | 實作是 `impl` 套件裡 final 的 `…UseCase`；邊界是 `…Input`／`…Output`；Request 是 `…Request` | CA-4、CA-16 |
| Gateway | 以 `Repository`、`Reader` 結尾，或叫 `EventStore`、`EventFeed` | DDD-8、CA-6、CA-11 ISP |
| Projection、ViewModel | 以 `Projection`、`ViewModel` 結尾 | CQRS-5、CA-9 |
| 用 JDBC 的類別 | `PostgresEventStore`、`PostgresReadModelStore`，其他的照第 0 節 4d 加進清單 | ES-1 |

這些靠名稱辨認的地方，第 9 節第 2 項會逐一補「確認真的有認到」的測試，避免換個名字就漏檢。

## 5. 領域模型（flow-analysis/entities）

### 5.1 聚合：看板流程（BoardFlow）

看板流程內含：
- 看板名稱、是否封存；
- 流程欄位：順序、名稱、階段；刪掉的欄位保留刪除前的階段；
- 卡住門檻；
- 每個工作項目的完整移動紀錄與目前的判斷結果；
- 已處理到的看板動態位置。

外部只能呼叫聚合根的方法（DDD-4）。

**值物件**（DDD-6）：

| 名稱 | 意思 |
|---|---|
| `BoardFlowId` | 值和看板管理的看板識別碼相同：只用識別碼互相參照（DDD-5） |
| `FlowColumnId` | 流程欄位的識別碼 |
| `WorkItemId` | 工作項目的識別碼 |
| `Stage` | 列舉：未分類、未開始、進行中、完成 |
| `StuckThreshold` | 卡住門檻，天數 |
| `ActivityPosition` | 看板動態的位置 |
| `WorkItemTitle` | 工作項目的標題 |
| `FlowBoardName` | 看板名稱 |
| `FlowColumnName` | 流程欄位名稱 |

名稱在實作計畫依用語表定稿。

### 5.2 業務規則（每條至少一支聚合測試）

標「使用者」的是你確認過的；標「預設」的是我先採的保守預設，你可以改。

| # | 規則 | 來源 |
|---|---|---|
| F1 | 每一欄有一個階段：未分類、未開始、進行中、完成；使用者可以替任何一欄改階段 | 使用者（做法 B）；四種階段是預設 |
| F2 | 新出現的欄位一律是「未分類」；未分類的欄位不影響任何開始或完成的判斷 | 預設 |
| F3 | 開始時間＝工作項目第一次進入「進行中」或「完成」欄的時間 | 預設 |
| F4 | 完成時間＝工作項目最近一次從非完成的欄進入「完成」欄的時間；之後移回非完成的欄就不算完成，再進入完成欄時重新記完成時間 | 預設 |
| F5 | 交付時間＝完成時間－開始時間；只有已完成的工作項目才有 | 預設 |
| F6 | 改了任何一欄的階段，所有工作項目的開始、完成、交付時間都照新設定從頭重算 | 使用者 |
| F7 | 停留時間＝離開某一欄的時間－進入那一欄的時間；只算已經離開的停留，被刪除不算離開 | 預設 |
| F8 | 卡住門檻是 1～365 的整數天數；沒設定就不判斷卡住；可以取消 | 預設 |
| F9 | 停在「進行中」欄、而且在同一欄待滿門檻天數，算卡住；其他階段都不算 | 預設 |
| F10 | 卡住在三個時機判斷：定時檢查（預設每 10 分鐘）、工作項目換欄或被刪除、改階段或門檻 | 預設 |
| F11 | 在「完成」欄被刪除的工作項目保留完成紀錄（團隊常把做完的卡片清掉）；在其他欄被刪除的，不算完成，也離開卡住清單 | 預設 |
| F12 | 欄位被刪除後保留它的階段，用來判斷曾經過那一欄的歷史；已刪除的欄位不能再改階段 | 預設 |
| F13 | 看板封存後，流程數字照常顯示、設定照常可以改 | 預設 |
| F14 | 看板上發生過的事一律接受、不拒絕；同一筆看板動態收到兩次只記一次（位置不比已處理位置新的直接略過） | 預設 |
| F15 | 時間一律用看板上實際發生的時間，不是流程分析收到的時間 | 預設 |

每週怎麼分組、平均怎麼算，是統計方式，不是業務規則（第 0 節 4c），列在第 7.4 節。

拒絕原因（只有使用者的指令會被拒絕）是一個列舉，名稱進用語表，由 Presenter 轉成中文。

### 5.3 領域事件（DDD-7：過去式、不可變）

每個事件都帶看板流程識別碼與發生時間：
- 記錄看板上的事，用看板上實際發生的時間；
- 使用者的決定與檢查，用 Use Case 從時間來源取得的時間（ES-4）。

| 類別 | 事件 |
|---|---|
| 看板上發生的事（防腐層翻譯過來的事實，帶看板動態位置） | `BoardFlowCreated`、`BoardFlowRenamed`、`BoardFlowArchived`、`FlowColumnAdded`、`FlowColumnRenamed`、`FlowColumnMoved`、`FlowColumnRemoved`、`WorkItemAdded`（含標題）、`WorkItemTitleChanged`、`WorkItemMoved`（含在來源欄的停留時間）、`WorkItemRemoved` |
| 使用者的決定 | `ColumnStageSet`、`StuckThresholdSet`、`StuckThresholdRemoved` |
| 聚合的判斷結果 | `WorkItemFlowResultChanged`（開始時間、完成時間、交付時間，各自可以沒有）、`WorkItemStuckStatusChanged`（變成卡住，或不再卡住） |

- **名稱配合既有規則**：全部用既有事件命名規則認得的九個過去式字尾（`EntitiesRules.EVENTS_NAMED_IN_PAST_TENSE`），所以這條規則不用改。
  - 「哪些是看板上發生的事實」不靠字尾區分，而是看事件有沒有帶看板動態位置：只有事實才帶。
  - 事件的類型名稱一寫入就不能改（ES-7），所以要在第一次寫入之前，先在用語表定稿。
- **為什麼判斷結果也記成事件**：查詢端與 Projection 都不准做判斷（第 3.2 節），所以每一次判斷的結果都要由聚合寫成事件。
- **重算時**：重算（F6）只替結果有變的工作項目新增 `WorkItemFlowResultChanged`，舊事件不動。

### 5.4 事件溯源的寫法

同第一階段第 5.4 節：
- 指令方法：檢查規則，決定產生哪些事件；
- 套用方法：只改狀態，不檢查、不會失敗；
- 載入聚合＝依序套用全部事件（ES-3、ES-4）。

## 6. Use Case 圈（flow-analysis/use-cases）

### 6.1 指令端

| Use Case | 誰呼叫 | 做什麼 |

| `RecordBoardActivity` 記錄看板動態 | 防腐層 | 把一筆看板上發生的事交給看板流程；看板流程還不存在就先建立 |

## 7. Interface Adapters 圈

### 7.1 三條路

1. **畫面**：和第一階段第 7.1 節相同，Controller → Input Boundary → Use Case → Output Boundary ← Presenter。
2. **背景同步**：
   1. 第 4 圈的排程每 2 秒呼叫一次防腐層。
   2. 防腐層呼叫看板管理的 `ReadBoardActivitiesInput`（「上次讀到的位置之後」），自己實作 `ReadBoardActivitiesOutput` 來收結果。
   3. 防腐層逐筆翻成流程分析的 Request Model，呼叫 `RecordBoardActivityInput`；它也實作 `RecordBoardActivityOutput`，從回覆得知這一筆是成功、版本碰撞還是失敗。
   4. 確認成功才前進讀取位置。
3. **定時檢查**：和畫面的請求同一個形狀，不新增轉接層套件。
   1. 第 4 圈的排程每 10 分鐘，請 Main 組裝 `ListBoardFlows` 的 Controller 與 Presenter，拿到全部看板流程的識別碼。ViewModel 只是識別碼字串的清單。
   2. 排程對每個識別碼，再請 Main 組裝 `CheckStuckWorkItems` 的 Controller 與 Presenter，各送一次。

第 4 圈的排程只呼叫第 4 圈自己定義的介面，由 Main 實作並接到第 3 圈。這和第一階段的 Spring 薄殼一樣，排程本身不含判斷，只是把清單逐一送出。

### 7.2 Presenter 與 ViewModel（CA-9）

ViewModel 只有字串、布林、列舉與它們的清單。Presenter 負責：
- 時間轉成顯示字串（時區由 Main 傳入，預設 Asia/Taipei）；
- 時間長度轉成「3.5 天」；
- 階段與拒絕原因轉成中文。

### 7.3 Gateway 轉接程式

- 流程分析的 `EventStore`：記憶體版與 PostgreSQL 版，契約測試各跑一次（CA-6、ES-2、ES-6）。看板管理的契約測試不共用：兩個情境各自的介面只是長得像，會各自演變（第 16 章「意外的重複」，DDD-2）。
- `BoardFlowRepository`：載入時重播，儲存時帶預期版本號寫入。
- 讀取模型：記憶體版與 PostgreSQL 版。
- 事件轉 JSON：固定類型名稱與格式版本，舊格式用 upcaster 轉換（ES-7）。
- 防腐層的讀取位置：記憶體版與 PostgreSQL 版。

### 7.4 Projection（CQRS-5、ES-8）

- **流程分析的 Projection**：
  - 從流程分析自己的 `EventFeed` 依序讀事件，維護四樣讀取模型：各欄的階段與目前張數、各欄停留時間的加總與次數、每週完成數與交付時間、卡住清單。
  - 只做第 0 節 4c 允許的加總、平均、計數，統計方式如下表。
  - 處理事件與更新處理位置在同一個交易內；同一個事件處理兩次結果不變。

  | # | 統計方式 | 由什麼守 |
  |---|---|---|
  | S1 | 每週從週一 00:00 起算，時區由 Main 傳入（預設 Asia/Taipei）；畫面顯示最近 8 週（含本週） | Projection 測試、查詢測試 |
  | S2 | 交付時間顯示最近 8 週內完成的工作項目的平均與最長；停留時間顯示每一欄已結束停留的平均 | Projection 測試 |
- **看板管理的 `BoardActivityProjection`**：只把領域事件翻成公布格式。
- 兩者都可以清空重播（ES-8）。

### 7.5 防腐層的細節

- **讀取位置**存在流程分析自己的資料表裡。
- **重複處理**：處理完一筆才前進讀取位置。如果在兩步之間當掉，下次會重送同一筆，由聚合依 F14 略過，所以不會重複計算。
- **出錯時**：技術錯誤（例如資料庫斷線）時，停在那一筆、寫日誌，下一輪再試；看板管理完全不受影響。看板上的事一律不會被業務規則拒絕（F14）。不認得的動態種類在編譯時就擋掉（第 4.4 節）。
- **版本碰撞**：碰到版本號不符（使用者剛好同時改設定），立即重試，最多 3 次。
- **監看缺口**：同步停住時目前只寫日誌。對外沒有訊號這件事，和既有的 #12 同一類，先記在那張單。

### 7.6 一致性說明（CQRS-6）

| # | 情況 | 會怎樣 |
|---|---|---|
| 1 | 在看板上操作 | 看板指令回覆成功時，看板動態紀錄已補到最新（同一個請求）。流程分析每 2 秒讀一次，所以流程分析頁大約 2 秒內看得到，處理時間另計 |
| 2 | 在流程分析改設定 | 指令回覆成功時，流程分析頁已是新的（同一個請求內補讀取模型，同第一階段）。重算整段歷史在同一個指令內完成 |
| 3 | 卡住 | 最多晚 10 分鐘才標上卡住。工作項目一換欄，下一次同步（約 2 秒）就從卡住清單消失 |
| 4 | 背景同步失敗 | 流程分析停在出錯的那一筆，之前的數字照常顯示，下一輪重試。看板管理照常運作 |
| 4b | 看板動態紀錄沒有更新成功 | 看板指令照樣回覆成功：事件寫入後的通知失敗不影響寫入結果（`NotifyingEventStore`，同第一階段 7.5 的第 2 種情況）。流程分析這段時間讀不到新動態，等看板動態紀錄在下一次看板指令成功後、或系統啟動時補上，再照常同步 |
| 5 | 背景同步與使用者同時改同一個看板流程 | 背景那邊自動重試；使用者看到「已被更新，請重新整理後再試」 |

六種情況（含 4b）各有一支整合測試（第 9 節）。

## 8. Frameworks & Drivers 圈與 Main

- **資料庫**：同一個 PostgreSQL。
  - 流程分析用自己的 schema `flow_analysis`，有自己的事件表、讀取模型表、兩個處理位置表（Projection 一個、防腐層一個），以及自己的資料庫版本紀錄。
  - 看板管理的表留在 `public` 不動，只新增 `board_activity_log`。
  - 理由：每個情境擁有自己的資料（DDD-2），資料庫結構檢查（ES-1）也能各自檢查自己的 schema。
- **事件表**：和看板管理相同的設計。全域序號、串流識別碼、版本號、事件類型、格式版本、內容、發生時間；`(串流, 版本)` 唯一（ES-6）；觸發程序拒絕修改、刪除與清空（ES-2）。
- **背景排程**：用 Spring 排程，在第 4 圈。同步間隔（預設 2 秒）與檢查間隔（預設 10 分鐘）由設定值調整。
- **Main**：新增流程分析的組裝。記憶體版或資料庫版同樣由 `kanban.storage` 切換。啟動時把流程分析的讀取模型補到最新（ES-8）。
- **前端**：
  - 前端的進入點（`main.ts`、路由、最外層版面、`package.json`、建置設定）搬到 `main/web-ui/`，成為前端的 Main（CA-8）。
  - 看板管理的畫面留在 `board-management/web-ui/`，流程分析的畫面放在 `flow-analysis/web-ui/`，各情境的畫面互不引用，只由進入點的路由接起來。
  - 理由：如果進入點留在看板管理，看板管理的畫面就要認識流程分析，方向反了。
  - CI 的前端路徑跟著改。
- **看板頁的入口**：看板頁多一個「流程分析」連結，由進入點的路由提供，看板管理的畫面元件不知道流程分析存在。

## 9. 驗證設計

延續第一階段第 9 節的 14 項。流程分析每一項都要有自己的一份，另加下列幾項。

1. **DDD-3 新增架構測試**（附違規樣本）：
   1. 看板管理不得引用流程分析的任何東西；
   2. 流程分析只有防腐層模組可以引用看板管理，而且只能引用 `usecases.queries.readboardactivities` 套件；
   3. 跨情境邊界上的型別只能是簡單資料（第 0 節 4b）。
   4. 防腐層套件 `adapters.boardactivity` 的角色規則。現有的角色規則（`AdapterRules` 的 Controller、Presenter 兩條）是靠套件名認對象的，管不到這個新套件，所以另外加一條：
      - 對流程分析只能呼叫 `RecordBoardActivityInput`；
      - 只能實作看板管理的 `ReadBoardActivitiesOutput` 與流程分析的 `RecordBoardActivityOutput`；
      - 用 JDBC 的只有讀取位置的儲存。
   5. 第 4 圈排程的角色規則：排程是新結構，而既有的「Spring 薄殼只能轉交」規則（`FrameworkRules.ENDPOINTS_ONLY_DELEGATE`）只管 `frameworks.web` 套件。依 `CLAUDE.md` 第 6 節第 4 點，另加一條同樣內容的規則管排程的套件。和薄殼一樣：
      - 只能使用 ViewModel 與第 4 圈自己定義的介面；
      - 不得引用 Use Cases 圈、Entities 圈；
      - 不得引用 Controller、事件庫、Projection、`adapters.system`，也不得引用防腐層。
2. **補強既有檢查**（每項附違規樣本，證明補強前擋不住、補強後擋得住）：
   - **用語表要分情境**（DDD-1）：每個情境的公開領域名稱，必須列在用語表裡自己那一節。現在的讀法不分情境（`Glossary.codeNames`），名稱只要出現在任一節就算過。
   - **CQRS-5「只有 Projection 能寫讀取模型」不靠名稱認**：現在靠 `ReadModelStore` 這個名稱與五個方法名稱認（`CqrsRules.READ_MODEL_WRITES`），換個名稱的儲存就擋不到。
   - **Gateway 辨認**（DDD-8、CA-6）：現在靠名稱結尾認（`Shapes.isGatewayInterface`）。流程分析的 Gateway 名稱不符合的話會漏檢，要改成不靠名稱，或加一支測試確認每個 Gateway 都被認到。
   - **模組相依測試**（CA-2、CA-3、CA-7、CA-16）：替流程分析的每個模組各加一支，包括防腐層模組只能 `requires` 第 4.2 節表上的模組。
   - **資料庫結構檢查**（ES-1）：`flow_analysis` 的寫入端只有事件表。
3. **聚合測試**：F1～F15 每條至少一支（統計方式 S1、S2 由 Projection 測試守），一律寫成 Given 已發生的事件／When 指令／Then 產生的事件（ES-5）。
4. **重算測試**（F6）：同一串看板動態，「先設定 A、再改成 B」的結果，必須等於「一開始就設定 B」的結果。
5. **防腐層測試**：每一種看板動態翻成哪個 Request Model；重送同一筆不重複計算。
6. **公布格式契約測試**：釘住每一種看板動態與它的欄位名稱、型別；可以新增，刪除或改名就失敗（第 4.4 節）。
7. **整合測試**：第 7.6 節六種情況各一支；看板動態紀錄清空重建後位置不變。
8. **瀏覽器實測（L4）**：在瀏覽器把第 2 節每一項實際走一遍，包括設定前後的數字變化與重算。前端進入點搬家之後，第一階段的瀏覽器實測結果就不算數了，所以第一階段的每一項操作也要重走一遍。
9. **CI**：每次推送跑全部自動檢查。

## 10. 邊界清單（CA-14，新增的部分）

| 邊界 | 隔開了什麼 | 為什麼會以不同理由改變 |
|---|---|---|
| 看板管理 ↔ 流程分析（看板動態） | 團隊怎麼用看板 ↔ 怎麼量測流程 | 前者因工作方式而改，後者因想看的數字而改 |
